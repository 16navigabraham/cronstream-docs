# Architecture

## Hook contract structure

Cronstream is a single contract, `CronstreamHook.sol`, inheriting from Uniswap v4's `BaseHook.sol`. A companion library, `TransientAccounting.sol`, contains Yul assembly helpers for all EIP-1153 transient storage operations.

```
/src
  CronstreamHook.sol          - master hook implementation
  libraries/
    TransientAccounting.sol   - TSTORE/TLOAD assembly wrappers
/test
  Cronstream.t.sol            - Foundry unit and integration tests
/scripts
  Keeper.ts                   - off-chain keeper automation
```

## Hook permission flags

Uniswap v4 encodes hook permissions into the hook's deployment address via bitwise flags. Cronstream registers the following callbacks:

| Callback | Purpose |
|---|---|
| `beforeInitialize` | Pool authorization gate - rejects any pool not on the whitelist |
| `afterAddLiquidity` | Record LP address and update liquidity ownership share |
| `afterRemoveLiquidity` | Scale down LP ownership on position exit |
| `afterSwap` | Measure fee surplus delta after each swap |
| `afterDonate` | Detect donated token surplus |

The `getHookPermissions()` function returns the corresponding `Hooks.Permissions` struct with these flags set to `true` and all others `false`.

## Pool authorization

In Uniswap v4, any address can deploy a pool that references a given hook contract. Without a guard, a malicious actor could bind Cronstream to a spam or illiquid pool - polluting the keeper's event feed and creating exploitable edge cases in the inline swap.

`beforeInitialize` acts as an access control gate. Only pools explicitly registered by the protocol administrator are permitted to bind to the hook:

```solidity
mapping(PoolId => bool) public isAuthorizedPool;

function authorizePool(PoolKey calldata key) external onlyOwner {
    isAuthorizedPool[key.toId()] = true;
}

function beforeInitialize(address, PoolKey calldata key, uint160)
    external
    override
    returns (bytes4)
{
    require(isAuthorizedPool[key.toId()], "Cronstream: POOL_NOT_AUTHORIZED");
    return BaseHook.beforeInitialize.selector;
}
```

This limits Cronstream's operational scope to a curated registry of institutional-grade asset pools (BUIDL, USDY, USYC, sUSDai) and eliminates the griefing surface entirely. New pools are added by the administrator after off-chain diligence on token contract behavior and liquidity depth.

### Role separation

Two distinct roles operate Cronstream with no overlap:

| Role | Actor | Function | Access control |
|---|---|---|---|
| **Protocol admin** | Cronstream multi-sig | `authorizePool()` - whitelists pool IDs before creation | `onlyOwner` |
| **Keeper** | Node.js EOA / any caller | `distributeYield()` - triggers yield distribution on active pools | None - fully permissionless |

The keeper cannot whitelist pools. The admin does not need to be online for distributions to run. A compromised keeper has zero ability to alter the pool registry or redirect yield - the worst outcome is a missed distribution that any other caller can fill.

## LP ownership matrix

Because the `PoolManager` singleton does not maintain an enumerable registry of LP addresses, Cronstream builds and maintains its own:

```solidity
// Persistent storage
mapping(PoolId => mapping(address => uint128)) public lpLiquidity;
mapping(PoolId => uint128)                     public totalLiquidity;
mapping(PoolId => address[])                   internal lpList;
mapping(PoolId => mapping(address => bool))    internal isLP;
```

When `afterAddLiquidity` fires, the hook writes the LP's delta to `lpLiquidity` and appends the address to `lpList` if it is a new entrant. When `afterRemoveLiquidity` fires, the hook scales down the LP's recorded amount.

Pro-rata share at distribution time is computed as:

```
lpShare = (lpLiquidity[poolId][lp] × surplusAmount) / totalLiquidity[poolId]
```

## Transient storage slots

All intra-transaction state - reentrancy locks, gas bookkeeping, and intermediate delta accumulation - is stored in EIP-1153 transient storage (Solidity 0.8.26+, Cancun EVM). These slots cost ~100 gas to write versus 20,000 gas for a cold SSTORE, and are automatically zeroed at the end of each transaction with no explicit cleanup required.

```solidity
// Custom EIP-1153 transient slot constants
bytes32 constant REENTRANCY_SLOT   = keccak256("cronstream.reentrancy");
bytes32 constant INITIAL_GAS_SLOT  = keccak256("cronstream.initial_gas");
bytes32 constant ACCUMULATED_DELTA = keccak256("cronstream.temp_delta");
```

The Yul assembly read/write helpers in `TransientAccounting.sol`:

```solidity
function tStore(bytes32 slot, uint256 value) internal {
    assembly { tstore(slot, value) }
}

function tLoad(bytes32 slot) internal view returns (uint256 value) {
    assembly { value := tload(slot) }
}
```

## The lock-callback state machine

The `distributeYield(PoolKey calldata key)` function is the only public entrypoint. Its execution is managed through a strict lock-and-callback sequence enforced by the `PoolManager` singleton.

### Entry

```solidity
function distributeYield(PoolKey calldata key) external {
    tStore(REENTRANCY_SLOT, 1);
    tStore(INITIAL_GAS_SLOT, gasleft());
    poolManager.unlock(abi.encode(key, tx.origin));
}
```

The reentrancy lock is set and the entry gas is recorded in transient storage before the `unlock()` call. The `PoolManager` halts all other external operations and routes control to `unlockCallback`.

### Inside `unlockCallback`

The callback receives the encoded `key` and `keeper` address. It executes the following sequence atomically:

**Step 1 - Surplus isolation.** The hook calls `poolManager.sync(currency0)` to force the `PoolManager` to register any balance increase from token rebases. The resulting positive delta represents the unassigned rebase surplus.

**Step 2 - Delta generation.** `poolManager.take(currency, address(this), surplusAmount)` transfers the surplus tokens to the hook. This creates a negative currency delta (the hook owes the pool).

**Step 3 - Gas calculation.** The hook computes the exact ETH owed to the keeper:

```
ΔTH = (Gas_start − Gas_end + Ω) × tx.gasprice
```

Where `Ω` is a constant overhead factor covering post-calculation execution cost. This is calculated using `INITIAL_GAS_SLOT` from transient storage.

**Step 4 - Inline ETH acquisition.** The hook executes an exact-output swap on a pre-configured ETH/stablecoin pool inside the same `PoolManager` session, acquiring the precise ETH amount calculated in Step 3. `poolManager.settle(stablecoin)` balances the stablecoin delta.

**Step 5 - Distribution and settlement.** ETH is transferred to the keeper (`payable(keeper).call{value: ethOwed}("")`). The remaining stablecoin balance is distributed to each LP address in `lpList` proportionally. All currency deltas must equal zero before the callback returns - the `PoolManager` enforces this invariant and reverts the entire transaction if `NonzeroDeltaCount != 0`.

### Exit

When `unlockCallback` returns, `REENTRANCY_SLOT` and all other transient slots are automatically zeroed by the EVM. The keeper's wallet balance has increased by the exact gas cost of the transaction. Each LP's wallet has received their yield share.

<Callout type="info">
  The entire distribution - surplus isolation, keeper reimbursement, and LP payouts - executes as a single atomic transaction. It either completes in full or reverts entirely. There is no partial distribution state.
</Callout>

## Compliance-resilient distribution loop

Institutional RWA tokens like BUIDL enforce on-chain transfer restrictions - a recipient address that has lost its KYC status will cause a `transfer()` call to revert. In a standard distribution loop, a single non-compliant LP address would revert the entire atomic transaction, freezing yield for every other LP in the pool.

Cronstream handles this with a try/catch escrow fallback. Each LP transfer is wrapped individually:

```solidity
mapping(address => uint256) public escrowedYield;

for (uint256 i = 0; i < lpList.length; i++) {
    address lp = lpList[i];
    if (lpLiquidity[poolId][lp] < MINIMUM_LIQUIDITY) continue;
    uint256 amount = (lpLiquidity[poolId][lp] * surplus) / totalLiquidity[poolId];

    try IERC20(yieldToken).transfer(lp, amount) {
        // success - yield pushed to LP wallet
    } catch {
        // transfer failed (KYC revoked, blacklist, etc.)
        // isolate yield and continue loop - other LPs are unaffected
        escrowedYield[lp] += amount;
        emit YieldEscrowed(lp, amount);
    }
}
```

If a transfer fails, the yield is parked in `escrowedYield` for that address. The LP can resolve their compliance status and pull the escrowed amount separately. Every other LP in the pool receives their distribution without interruption. The `MINIMUM_LIQUIDITY` threshold also prevents dust positions from bloating the `lpList` and inflating gas cost.

## Off-chain keeper

The `distributeYield()` entrypoint carries no access control - it is fully public. Any address that calls it receives exact gas reimbursement from the yield pool, making the protocol infrastructure-neutral by design.

Cronstream's primary automation client is a Node.js keeper service running an EOA wallet on each target network. It subscribes to pool events via WebSocket RPC (`ethers.js` / `viem`), monitors the pool's yield balance, and autonomously submits `distributeYield()` transactions when the threshold is crossed.

### Gas self-funding loop

The keeper requires no external treasury beyond a standard ETH operational float. When it calls `distributeYield()`:

1. It spends native ETH to submit the transaction
2. The hook's `gasleft()` calculation computes the exact runtime gas cost
3. The hook executes an inline exact-output swap to acquire the precise ETH amount
4. The ETH is transferred to `tx.origin` (the keeper's EOA) in the same transaction

The keeper wallet is fully reimbursed within the same block. The slight overhead factor `Ω` in the gas formula means the keeper accumulates a small net surplus over time.

### Why not a cross-chain reactive contract?

Cronstream evaluated deploying a Reactive Network smart contract as the automation layer. Three structural incompatibilities ruled it out:

**1. The gas refund paradox.** Cronstream's `gasleft()` mechanism calculates the exact ETH owed to the caller and transfers it to `tx.origin` inline. If a cross-chain relayer proxy is the entity calling `distributeYield()`, the relayer contract address becomes `tx.origin`. Cross-chain relayer proxies are not designed to absorb arbitrary ERC-20 or native token payouts mid-transaction - the refund is trapped or rejected, and the self-funding loop breaks.

**2. Secondary token dependency.** Keeping a Reactive Network contract operational requires maintaining a balance of REACT tokens on the Reactive chain to pay for cross-chain message passing. This introduces a second operational token, a separate funding pipeline, and a failure mode - insufficient REACT balance - that has nothing to do with the protocol's yield distribution logic.

**3. Non-deterministic latency.** Cross-chain consensus queues and bridge settlement introduce variable latency between a rebase event and the distribution call. A local WebSocket subscriber responds within the same block the threshold is crossed.

The Node.js keeper eliminates all three issues. Gas refunds land directly in the keeper's EOA. The keeper spends native ETH on the destination chain and immediately recovers it. RPC monitoring has no multi-chain intermediaries.

### Sponsored mode

When an ecosystem foundation covers keeper costs via a paymaster or pre-funded relayer:

- The keeper calls `distributeYield()` with `sponsored = true`
- The inline ETH swap is skipped entirely
- 100% of yield flows directly to LPs with no swap overhead

No contract changes required - the mode is a call-time parameter.

### Permissionless fallback

None of this changes Cronstream's permissionless properties. `distributeYield()` has no `onlyKeeper` modifier. Any caller - an MEV searcher, the asset issuer, another bot - can call it at any time and collect the gas reimbursement. The keeper is the reference client, not a gatekeeper. If it goes offline, distributions continue uninterrupted via open market execution.
